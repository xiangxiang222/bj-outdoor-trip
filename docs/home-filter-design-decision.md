# 首页筛选设计复核

日期：2026-11-02。状态：已实现，尚未合并或发布；微信真机待验收。

## 结论

小程序首页、独立线路页和网页版统一使用一组单选的“出游偏好”，保留天数与关键词；上方三张灵感卡是同一组偏好的视觉入口。后台同步提供偏好配置与线路命中预览。分类与标签整理完整后，再评估是否升级为“想看什么”和“想怎么玩”两个维度。

原先“主题＋玩法”的并列筛选已被替换，避免把语义重复的分类、标签再次取交集。后台线路仍维护真实分类与标签，偏好根据配置自动匹配，不再让运营维护第二份容易分歧的线路归属。

## 改造前的审计依据

- 分类有长城、登山、山水、玩水、文化、草原、海滨；默认玩法有徒步、登山、玩水、亲子、摄影、露营、文化、看星空、团建。登山、玩水、文化重复，亲子属于适合人群，团建属于组织方式。
- 旧版 `/routes` 的玩法参数匹配“分类等于玩法，或标签包含玩法”；主题再与它取交集。因此两组并不是相互独立的属性。此旧参数仅为兼容旧客户端保留，新客户端不再发送。
- 仓库 30 条种子线路中，“主题：登山”有 4 条，“玩法：登山”有 5 条。当前三个主题与九种玩法共 27 种组合，其中 18 种为空。此统计只反映种子数据，不能解释为空的组合一定不适合出游。
- 例如海滨线路《秦皇岛北戴河·山海关》没有玩水、摄影标签；漂流线路也不一定有玩水标签；“星空”与“看星空”不统一。组合筛选会放大漏标问题。
- 设计审计时只读查询线上公开 `/api/routes` 返回 2 条线路，公开玩法接口仍返回 9 项。这是当时的公开结果，不代表当前或完整后台库存。

## 已实现布局与交互

| 层级 | 展示与含义 |
| --- | --- |
| 上方灵感卡 | 长城卡、山野卡、海边卡，分别进入长城、徒步登山、海边偏好 |
| 出游偏好 | 全部、长城、徒步登山、海边、更多；一次选一个出游方向 |
| 行程天数 | 不限、1日、2日、3日、4日及以上，与偏好组合 |
| 搜索 | 搜目的地或线路，与偏好、天数组合 |
| 已选条件 | 展示偏好、天数、关键词；可分别取消或全部清空 |

“更多”展开当前关键词、天数下有线路覆盖的其他偏好，例如亲子、摄影、露营、草原、人文；选中后替换之前的偏好。已选偏好即使变为零结果仍保留可见，常用项、名称及顺序由后台控制。

三张卡和下方按钮使用同一份偏好配置和同一个选择状态。偏好不是后台分类字段的改名：例如“徒步登山”匹配分类“登山”，或完整标签“徒步”“登山”；长城匹配分类或完整标签“长城”。分类与标签规则之间取并集，偏好与天数、关键词之间取交集，不使用单字模糊搜索推断线路属性。

点击任一偏好入口，仅替换偏好，保留用户已选天数、关键词和团期日期。点击热门目的地则替换关键词、移除原偏好，保留天数与团期日期；清空线路条件不会清空团期日期。团期列表的组织类型与玩法条件不作为线路的隐藏条件。

上方卡片沿用可打断的缓动定位；列表内切换只更新结果，不滚动页面，仅在偏好行内横向显示当前选择。无结果时保留条件，提供单项移除和清空入口。数量依据当前关键词与天数、忽略当前偏好计算；加载中或接口失败时隐藏数字并提供重试，不把未知数量显示为零。

偏好已被后台停用或不存在时，服务端明确返回不可用错误；客户端清空旧线路、保留已选条件并提示重新选择，同时刷新配置。已知名称会保留用于提示，不会静默改为全部线路。后台停用三张卡对应的偏好后，成功刷新配置的客户端隐藏相应卡片。

这一阶段的代价是不能同时指定“长城＋摄影”。它适合当前线路覆盖较少、标签尚不完整的阶段，不能当成长期放弃组合筛选的理由。

## 后台与接口

- “偏好与标签 → 出游偏好”管理稳定标识、名称、常用项、排序、启停状态、精确分类和标签规则；创建后标识不可修改，删除操作为停用。配置至少有一条匹配规则。
- 原玩法标签保留在“发团标签”，供团期发布使用。它不再直接决定前台线路偏好选项。
- “线路管理”支持按前台偏好检查线路；列表显示命中的已启用偏好，编辑分类和标签时实时预览命中结果。预览不改变审核或上架状态。
- 后台读取沿用 roster 权限，写入沿用 ops 权限；前台选项及数量仅统计公开可见、已审核、已上架的线路，并沿用排除活动线路的规则。
- `GET /route-preferences?q&days` 返回启用选项及当前基础条件下的数量；`GET /routes?preference&q&days` 查询线路。前台不再发送 `category` 或 `tag`。
- `route_preferences` 独立存储规则，服务启动时幂等初始化默认项；已编辑或停用的默认项不会被重置。旧客户端 `category/tag` 请求保持兼容，与新 `preference` 混用则明确报错。

## 验证及发布约束

服务端 361 项、网页 372 项、小程序相关 102 项回归通过，网页生产构建、小程序语法和包体检查通过。小程序首页与独立线路页共 20 组实际 WXML / WXS 编译及 WXSS 浏览器兼容预览，覆盖窄屏、深色、英文大字、零结果和数量失败；这些预览不等于微信真机验收。

发布顺序必须为后端先行，确认 `/api/route-preferences` 返回合法配置，再更新网页及发布小程序。`scripts/deploy.sh` 已调整为先重启后端并检查线路与偏好接口，再构建线上网页，避免新版前端请求到忽略 `preference` 的旧服务。本轮只修改代码和执行临时／内存数据库测试，没有执行部署、修改真实数据库或发布小程序。

## 后续升级条件

先整理线路属性，再开放两个独立维度：

- 想看什么：长城、山地、海滨、草原、湖溪、人文景观；一条线路允许具备多个景观属性。
- 想怎么玩：徒步、露营、游船、漂流等活动。登山与徒步的边界应按产品定义合并或明确区分，体力要求放在强度属性中。
- 亲子放入适合人群，企业团建沿用组织类型入口；不混在活动列表里。

升级前需要完成标签同义词、明确的属性匹配、编辑与审核入口、存量线路核实及组合数量接口，取消玩法对旧分类字段的兜底。不能仅把“登山”改名为“山野”，继续使用相同混合数据。

若支持同组多选，应明确“海滨或草原”是在找任一风景；不同组再组合为“这些风景中适合露营的线路”。同组并集、跨组交集是常见的分面筛选方式，可参考 [Baymard 的多值筛选研究](https://baymard.com/blog/allow-applying-of-multiple-filter-values)与 [Algolia 的分面筛选说明](https://www.algolia.com/doc/guides/managing-results/refine-results/faceting)。这些资料提供交互参考；当前阶段收敛为单一偏好的建议，来自本项目的分类与线路覆盖审计。
