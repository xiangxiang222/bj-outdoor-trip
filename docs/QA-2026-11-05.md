## 问题清单

### P1-01：公司统一结算与支付回调落账失败

**复现步骤：** 公司发起人发布并通过审批 → 至少 2 人报名 → 发起人点击“公司统一微信支付”。

预期：所有应付报名结算成功，订单和支付流水一致，重复请求不重复收款。

实际：`POST /api/pay/company-settle` 返回 **500**，`UNIQUE constraint failed: payments.trade_no`。API 的 3 人及浏览器的 2 人场景都复现；明细事务整体回滚，所有报名仍为 `company_pending`，没有支付流水。浏览器上也没有可见的失败提示，见[公司结算截图](./qa/2026-11-05/company-settlement-result.png)。

专项探针还验证了**单人公司团的非 mock 支付协议分支**，网关仍完全模拟：创建公司主支付单 → 发成功签名通知 → 主单先被改成 `success`，写入报名分摊明细时发生同号唯一键冲突 → 首次通知回 FAIL；重试通知回 SUCCESS，但报名仍为 `company_pending`；查询确认接口却给出 `paid/already`。这证明业务处理可能出现主单成功、报名未结算的不一致；本轮没有发生真实扣款。

原因定位：[payment.js](../server/src/services/payment.js#L573) 的 `applyCompanyShares` 为每份明细复用同一个 `trade_no`，与 [db.js](../server/src/db.js#L507) 的唯一索引冲突；[回调公司分支](../server/src/services/payment.js#L712) 在明细事务之前将主单设为成功，重试又被成功状态提前返回。

建议验收条件：主支付单与报名分摊有独立、可追溯的标识；公司支付结算状态一致且可重试恢复；覆盖 1/2/3 人、重复通知、失败后重试和页面报错提示。

### P1-02：同一付款人分两笔支付后退款可能同号冲突，并留下部分状态

**复现步骤：** 同一人对一个报名分两笔付款 → 本人取消报名退款。

API 主流程自然复现了取消接口 500。专项探针仅在退款阶段固定 `Date.now`，稳定模拟两个退款切片在同一毫秒生成编号，得到：

- 两笔源付款的 `refunded_amount` 均已被更新为全额。
- 仅第一笔退款流水成功写入；第二笔触发 `payments.trade_no` 唯一键冲突。
- 报名仍为 `joined/paid`，取消没有完成，账本和报名状态不一致。
- 注入模拟退款服务后，两个不同原支付单收到相同的 `refundNo`；真实微信网关会如何拒绝或幂等处理没有在本轮验证。

根因：[编号生成](../server/src/services/payment.js#L39) 只包含前缀、毫秒和用户 ID；[退款循环](../server/src/services/payment.js#L298) 对同一付款人的多笔退款可能生成相同编号，且退款流水、源单累计和取消状态未共同保证一致性。**本结论是同毫秒条件下的已复现缺陷，不代表所有取消都会失败。** 对照的单笔支付 89、退款 89，取消后状态正确，通过。

建议验收条件：不同原支付切片具备唯一且可重试的退款编号；失败后可恢复一致状态；重复取消不重复退款；增加同付款人多笔支付的回归覆盖。

### P2-03：导游行程完成后的状态边界不完整

当天的未开始行程可直接完成；完成后导游仍能新建签到轮次，均返回 200。[完成逻辑](../server/src/services/aftertrip.js#L23) 未要求先开始，[签到逻辑](../server/src/services/trip-run.js#L150) 未拦截 `completed_at`。建议明确并约束完成后的写操作。

另观察到当天 0 人、仍在招募的团可以通过后台正式开团。后台是否允许强制开团属于规则待确认项，本报告不将其计作通过或确定缺陷。

### P2-04：非生产 mock-success 缺少归属和状态检查

非生产环境，另一登录用户知道已退款流水编号后，可调用 `/api/pay/mock-success` 将该流水改回 `success`。生产环境已有 403 限制，本轮没有发现该端点能用于生产真实支付。建议测试环境也限制操作权限及合法状态；本轮正向支付没有使用此端点。

## 当前规则与测试边界

- 已上架线路新增排期 `/schedules` 当前自动批准；新线路 `/trips` 才进入后台审核。浏览器发布通过不等于执行了人工审批，人工审批由 API 场景覆盖。
- 当前普通账号填写公司/学校名称即可发布对应类别排期；没有独立企业营业执照认证接口。“团体资料审核通过”不等于企业资质核验通过。
- 高校报名资格取决于设置的受众范围。本轮主流程为本校学生团；未认证和外校账号被拒绝。公开公司团未校验员工身份，但只有发起人可以统一结算。
- 公司团在挂账状态下也能成团、进行导游操作，本轮按现有规则独立验证这些操作；公司的完整支付闭环仍失败。
- **本轮没有验证微信小程序原生界面、iPhone 正式版、真实微信支付/退款、短信送达、真实实名供应商、真实跨日、压力或并发负载。** 此报告不能作为这些项目的验收结论，也不覆盖此前的分享卡片图片问题。
