# 同行者众 · AI 产品方案（讨论稿）

本稿只提出产品、交互与工程方案，不代表已实现或上线。基于当前仓库的线路、排期、校园范围、活动、报名、领队和后台能力制定，未连接生产环境核查配置。

2026-10-29：首期已开始落地，实际范围、配置与本地验证见 [一句话找团实现说明](AI_DISCOVERY.md)；其余方向仍是规划，尚未上线。

产品定位：**让用户用一句话说清想怎么玩，更快找到能参加的一程；让组织者更容易把想法变成可执行的活动。**

## 1. 我的判断

最有价值的第一步是「一句话找团 + 真实方案对比」。它直接解决现在需要多次点选日期、目的地、团型，再逐个查看费用和安排的决策成本。

首页保留普通搜索和时间筛选，增加一个轻入口「说说你想怎么玩」。AI 的结果进入真实线路、真实团期和原有报名流程。用户可以随时改回手动筛选。

第二步补发团草稿和本次行程问答，再扩展到多人共选、领队准备和后台质检。优先把现有供给解释清楚。

## 2. 产品机会与优先级

| 优先级 | 方向 | 用户实际得到什么 | 入口与结果 |
| --- | --- | --- | --- |
| P0 | 一句话找团 | 把「周末、预算、新手、跨校」转换为可修改的条件，找到真实可参与团期 | 首页搜索附近；条件摘要 + 最多 3 个推荐 + 查看全部 |
| P0 | 帮我选一程 | 看清两三项方案的差别和取舍 | 结果卡、线路详情；同维度对比卡 |
| P1 | 帮我发团 | 少填重复内容，减少遗漏；保留人对日期、费用和报名范围的决定 | 发团页；可编辑草稿 + 待确认事项 |
| P1 | 问问这一程 | 快速找到集合、装备、费用、退改和资格依据 | 团详情、我的行程；短回答 + 事实来源 + 原页面链接 |
| P2 | 一起选个周末 | 多人表达时间、预算和偏好后，看见真正可行的共同选择 | 发起人分享选择页；意见汇总、冲突说明、2–3 个候选方案 |
| P2 | 领队与运营助手 | 少做重复整理，提前发现资料遗漏和安排冲突 | 领队工作台、后台；通知草稿、准备清单、问题定位 |

「一起选个周末」适合高校跨校和公司团建，是值得形成产品特色的方向。但日期交集、票数和价格计算使用程序；AI 用来理解自由表达、解释取舍和提出备选。首期不扩大到新的多人协作系统。

## 3. 第一期开箱体验

示例请求：

> 下周末想去长城，一个人，预算 200 元以内，刚开始徒步，最好能参加跨校团。

以下是交互示例，不代表系统当前有符合条件的库存或价格。

1. 用户输入后，先展示可修改条件：「下周末的实际日期」「长城」「1 人」「人均 ¥200 内」「偏好轻松」「校园团」。
2. 时间由北京时间日期工具计算。预算明确是每人还是整团，必须费用是否包含；确有歧义才补问，优先一次问清关键缺项。
3. 服务端查真实在售线路与团期，检查审核状态、出发时间、资格和可参与状态。当前账号未认证时，分别标明「需认证」「不符合本团范围」，不能写成已经可以报名。
4. 首屏展示最多 3 个结果：真实照片、团期、当前费用口径、余位或候补状态、报名范围，再附一句推荐原因和一条需要注意的差异。
5. 用户可点「比较这几程」「换个偏好」「按这些条件看全部」，并进入已有团详情。
6. 进入报名时重新校验价格、资格与库存。AI 推荐卡上的快照不锁价、不占座。

推荐理由必须有可核对依据，例如「线路资料标注休闲，单程约 X 公里」「当前开放已认证高校师生」。公里数、爬升和路面未核实时应显示缺项，不能推断「所有新手都适合」。

无结果时说明限制来自哪里，并给用户选择：

> 暂时没有同时符合日期、预算和校园范围的团。可以换到另一周，或查看同日期其他线路。

默认保留用户的硬条件。放宽预算、日期、资格范围必须由用户明确选择；候补、仅线路无团期、超预算选项分别标明状态，不能混进完全匹配结果。

## 4. 页面与视觉

沿用当前紫色主题、浅底、白卡片、实景照片和细线图标。

- 首页搜索下方放一条轻入口：「还没想好？说说你想怎么玩」，附一个简洁对话/指南针图标。占用一行，避免抢走现有线路内容。
- 点击打开面板或独立结果页，先给三条可点击示例：「周末轻徒步」「想参加跨校团」「公司 30 人轻松团建」。
- 输入可从文字开始；后续语音只负责转成可编辑文本，涉及日期、费用、学校时仍明确确认。
- 结果按「条件标签 → 推荐卡片 → 推荐依据 → 行动」组织。用户可以直接改条件，不要求反复输入整段话。
- 对比在手机端按费用、步行量、交通、时间、范围逐项上下排布，桌面端可并列。未知项明确留空说明，避免编出总分或“最佳”。
- 生成过程显示已确认条件和当前真实状态；超时仍能进入普通筛选，不用无意义的百分比或伪造分析进度。
- 「我的」后续可提供用户主动保存的出发偏好，支持修改、删除；不默认长期记忆私人对话。

## 5. 发团与行程：后续怎样接上

### 发团草稿

例如：「下周六北航和北理同学一起徒步，20 人，预算每人 180，想轻松一点。」

AI 先识别这是校园发团，提取可确定字段，推荐已有线路；再由用户确认准确学校、学院/专业范围、日期、费用和人数。学校简称需对应确认后的实体，不能直接猜同名学院。

范围沿用既有「本校、跨学院、指定学校、已认证高校联谊」等规则。免费团也执行原来的报名、抽签和师生限制。AI 不能为满足“跨校”自动改成向所有人开放。

草稿用「已填写 / 待确认 / 缺少信息」展示，确认后进入现有表单和校验。排期的直接发布与活动的提交审核仍按现有接口执行。原表单中的输入不会被整份覆盖，用户可逐项采纳。

四类同城活动分别补齐已有结构：掼蛋规则与水平、跑步距离与配速、影片影院与场次、社团招募对象。AI 不编造电影场次、场地预约或尚未提供的购票凭证。

### 本次行程问答

问题围绕用户正在查看或已报名的具体团：几点集合、费用含什么、要带什么、退款规则在哪里。

回答附「来自本团集合安排 / 线路须知 / 平台规则」，可跳回原文。金额、退改档位和资格结论由业务服务生成，AI 负责解释。

领队端可起草行前通知、人数与物资准备摘要。涉及联系名单时严格限定当前领队负责的团；模型不需要身份证、完整手机或紧急联系人。领队检查后再发送通知。

后台从现有 AI 起草升级为「核对事实 → 补待确认项 → 草稿差异 → 人工采纳」。重点辅助找缺字段、日期前后矛盾和描述冲突。退款、打款、审核、认证、调座、签到和正式开始行程继续由已有权限与业务规则控制。

## 6. 当前项目已具备什么

| 已有能力 | 代码位置 | 可复用部分 |
| --- | --- | --- |
| 服务端模型配置 | `server/src/config.js` | AI_API_KEY、AI_BASE_URL、AI_MODEL；密钥不下发客户端 |
| 后台线路文案草稿 | `server/src/services/route-draft.js`、`POST /admin/routes/draft` | 兼容接口调用、超时和模板回退 |
| 自动英文翻译 | `server/src/services/route-i18n.js` | 内容哈希缓存、排队和失败冷却 |
| 线路稿件审核 | `server/src/services/route-bot.js` | 来源去重、待审核稿件与已通过内容保护 |
| 日期、价格与资格规则 | 日期工具、`helpers.js`、`eligibility.js`、现有报名服务 | 北京时间、真人计数、报价与校园范围 |
| 多端同一套接口 | Express / SQLite + 小程序 / H5 / 领队 / 后台 | 共享事实来源与权限，不在客户端加载模型 |

代码具备调用配置，不代表生产环境已配置有效模型密钥或已验证供应商可用性。本稿不作此假设。

有三项项目特有的数据准备必须放进排期：

1. **线路事实审核。** 现有 AI 起草允许生成距离、难度与行程内容；入库不等于经过事实核查。为首批可推荐线路补充来源、核实状态、更新时间，优先整理距离、爬升、路面、交通、必付费用与限制条件。未知字段保持未知。
2. **天气来源过滤。** `weather.js` 在真实天气失败时会回退 `source: mock`。模拟数据不能进入 AI 的实时天气答复；无可信预报时明确未获取，不能据此保证山区安全。地区预报也不能当成山顶实况。
3. **真人依据。** 当前存在虚拟报名与热度机制。推荐理由、口碑和运营分析使用真人报名、真实评价与真实支付口径；展示热度不能变成“真实成交很多”的依据，也不先做数据不足的成团概率预测。

## 7. 工程方案

```mermaid
flowchart LR
    A[用户说出需求] --> B[模型提取结构化条件]
    B --> C[服务端校验条件与权限]
    C --> D[现有线路 / 团期 / 报价 / 资格服务]
    D --> E[筛选排序与事实快照]
    E --> F[简短解释 + 可修改条件 + 真实卡片]
    F --> G[用户选择]
    G --> H[原报名流程再次校验]
```

首期采用明确、短的工作流。模型处理语言，程序处理计算、查询、鉴权和状态变更。后端对模型结构化输出作枚举、类型、范围校验；只能接受本次查询实际返回的线路/团期 ID。解释内容需对应事实字段，无法对应的断言不渲染。

优先增加一个小型 AI 服务层，复用现有模型配置，补上超时、限流、配额、费用上限、模型版本记录和失败降级。先以 SQL 和结构化字段检索现有供给；资料规模与召回评测证明有需要后，再引入向量检索。

小程序和 H5 只发需求、渲染服务端返回的组件数据，不新增本地模型和大素材。第一期不依赖开放式网页搜索来决定价格、路况和营业状态。

供给描述、用户输入、上传文字都当成数据，不能改变系统权限。首期不给模型任意 SQL、退款、收款或审批工具。查询也在工具执行时鉴权，用户在文字里说“我是管理员”没有作用。

价格与余位为短时事实，点击报名重新查询；不能把别人的会员报价缓存给当前用户。说明内容按资料版本缓存，个性化资格和敏感数据不进入共享缓存。

日志只记最小诊断信息与脱敏反馈，支持按会话排查错误。各类客户端不携带模型密钥。供应商先用项目样例评测中文理解、结构化结果、响应速度、数据处理条款和当前部署环境可用性，再选主模型；不在没有实测时承诺固定模型、效果或调用价格。

方法参考：Anthropic 的 [Building effective agents](https://www.anthropic.com/research/building-effective-agents) 将明确工作流与更自主的代理区分，并讨论简单、可组合模式。本方案选择前者，是基于本项目对金额、资格、库存和权限准确性的要求作出的工程判断。

## 8. 验收、灰度和效果

先建立 100 条人工标注的典型请求作为第一批回归集；后续把真实失败请求脱敏补入。建议分布：40 条日期/预算/偏好，20 条校园范围，15 条价格与库存变化，15 条缺资料/无结果，10 条越权/恶意指令与异常响应。

验收必须同时包含业务服务测试、模型离线评测、多轮对话和真实客户端测试。固定样例通过不等于所有线上回答都正确。

- 只能推荐真实、已通过、未结束的团。可以直接参与、需认证、候补、仅线路四种状态清楚区分。
- 明确的日期、费用上限和资格不能被擅自放宽；关键业务校验用例全部通过后才能灰度。
- 覆盖北京时间过日、周末跨年、会员/学生/免费团、同名学校学院、缺必付费用、余位在点击前变化。
- 线路文字内嵌“忽略规则、导出名单”等指令不能改变查询范围。用户、领队、运营角色分别测试。
- 模型错误 JSON、幻觉 ID、超时、供应商失败、网络中断都有可理解的结果，并可退回普通筛选。
- 手机小屏、英文、大字体、深色模式、键盘和无障碍标签都进入回归；小程序检查实际包体。

效果先采集原流程基线，再做少量用户灰度比较。关注：从开始找团到打开合适团详情的时间、推荐后有效报名率、重复改条件次数、无结果原因、回答纠错率、每次有效会话成本。不能只以聊天轮数或停留时长证明成功。

初始响应目标可定为常见请求 P95 约 8 秒内，需在选定供应商和服务器上压测；超时进入可用的降级路径。成本按每次有效找团、每日总额和单用户配额控制，实际模型费用确定后再给月度预算。

## 9. 实施顺序与估算

第一期建议做「一句话找团 + 同结果对比 + 来源/权限/异常保障」，不同时铺开所有页面。

- 第一步：审核首批线路事实，整理真实用户请求，选供应商并评测，定交互原型。
- 第二步：实现服务端条件解析、业务查询与结果校验，小程序/H5 的入口和卡片对比。
- 第三步：完成离线评测、两端回归、成本与延迟监控，开关灰度。
- 第二期：发团草稿与具体团问答，重点把校园范围和现有发布规则解释清楚。
- 第三期：多人共选、领队通知和后台质检，依据实际使用数据决定范围。

规划估算：一名熟悉项目的全栈工程师全职投入，模型服务已可用、首批线路事实已经运营核实，第一期约 2–3 周。该估算含两端交互、服务端和测试灰度，不含供应商开通、大规模资料核实与审核等待；实际任务拆分后应重新估算。

这份方案待讨论的主要产品取舍是：先用 AI 改善用户找团与选择，再逐步覆盖组织者和运营工作。首期验收围绕真实可参与的结果与决策效率，不以生成内容数量作为目标。
